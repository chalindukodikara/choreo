# Plan: Portable Layer Cache Registry for Rootless CI Workflows

## Goals

- Add a portable, in-cluster layer cache registry for workflow builds.
- Use `registry:2` directly, not the current k3d-only external registry install.
- Keep the cache registry separate from the final image registry.
- Make the cache registry optional and disableable from Helm.
- Make caching optional and disableable from workflow templates because templates are applied separately.
- Add layer caching for:
  - Dockerfile builds using BuildKit.
  - Dockerfile builds using Buildah.
  - Buildpack builds using the rootless Podman/daemon approach.
  - Buildpack builds using the CNB lifecycle approach.

## Naming

Use a dedicated service in the workflow-plane namespace:

```text
cache-registry.openchoreo-workflow-plane.svc.cluster.local:5100
```

Use port `5100` for the cache registry service to avoid confusion with the existing final image registry service, which commonly uses `5000`.

For k3d only, an optional host port can expose this as a debug convenience. The workflow templates must use service DNS, not `host.k3d.internal`.

## Architecture

Add a `registry:2` deployment to `install/helm/openchoreo-workflow-plane`.

Resources:

- `Deployment/cache-registry`
- `Service/cache-registry`
- `PersistentVolumeClaim/cache-registry`
- Optional `Secret/cache-registry-auth`
- Optional `ConfigMap/cache-registry-config`

The registry is a writable layer cache registry. It is not a pull-through mirror.

Pull-through mirroring can remain separate under `install/k3d/registry-cache`, but the build cache design must not depend on node-level container runtime mirror configuration because managed clusters may not allow it.

## Helm Values

Add registry infrastructure values under the workflow-plane chart. Use `cacheRegistry` for the registry deployment and reserve workflow-level `buildCache` fields for CI workflow parameters.

```yaml
cacheRegistry:
  enabled: false
  name: cache-registry
  image: registry:2
  port: 5100
  service:
    type: ClusterIP
  endpoint: cache-registry.openchoreo-workflow-plane.svc.cluster.local:5100
  tls:
    enabled: false
  auth:
    enabled: false
    existingSecret: ""
  persistence:
    enabled: true
    size: 50Gi
    storageClassName: ""
  resources:
    requests:
      cpu: 50m
      memory: 64Mi
    limits:
      cpu: 200m
      memory: 256Mi
  garbageCollection:
    enabled: false
```

Disable path:

```yaml
cacheRegistry:
  enabled: false
```

When disabled, Helm must not install the cache registry Deployment, Service, PVC, Secret, or ConfigMap.

## Registry Configuration

For the first implementation, use plain HTTP inside the cluster:

```yaml
version: 0.1
log:
  level: warn
storage:
  filesystem:
    rootdirectory: /var/lib/registry
  delete:
    enabled: true
  maintenance:
    uploadpurging:
      enabled: true
      age: 168h
      interval: 24h
http:
  addr: :5100
```

`delete.enabled` is needed for future cleanup jobs. `uploadpurging` prevents incomplete uploads from accumulating forever. Full registry garbage collection can be added later as a maintenance job or runbook.

Production hardening can add TLS and auth later. The workflow scripts should already accept these fields:

- `cache-registry`
- `cache-insecure`
- `cache-auth-secret`

This avoids changing the workflow contract later.

## Workflow Template Disable Model

Because workflow templates are applied separately, do not rely only on Helm values.

Every rootless build template should accept cache parameters with safe defaults:

```yaml
inputs:
  parameters:
    - name: cache-registry
      default: "cache-registry.openchoreo-workflow-plane.svc.cluster.local:5100"
    - name: cache-scope
      default: ""
    - name: cache-insecure
      default: "true"
```

Rules:

- If `cache-registry` is empty or `"none"`, do not probe and build without caching.
- If `cache-registry` is set, probe `http://$CACHE_REGISTRY/v2/` at build startup.
- If the probe succeeds, enable cache flags.
- If the probe fails, log the miss and build normally without caching.
- CI workflows generated by Helm can pass `"none"` when `.Values.cacheRegistry.enabled=false`.
- Plain YAML users can enable caching automatically by deploying the cache registry at the default service DNS.
- Plain YAML users can explicitly disable caching by passing:

```yaml
cache-registry: "none"
```

Runtime probe pattern:

```sh
CACHE_REGISTRY="{{inputs.parameters.cache-registry}}"
CACHE_ENABLED="false"

if [ -n "$CACHE_REGISTRY" ] && [ "$CACHE_REGISTRY" != "none" ]; then
  if command -v wget >/dev/null 2>&1 && wget -q --spider --timeout=3 "http://${CACHE_REGISTRY}/v2/" 2>/dev/null; then
    CACHE_ENABLED="true"
  elif command -v curl >/dev/null 2>&1 && curl -fsS --max-time 3 "http://${CACHE_REGISTRY}/v2/" >/dev/null 2>&1; then
    CACHE_ENABLED="true"
  else
    echo ">> Cache registry not reachable at ${CACHE_REGISTRY}, building without cache"
  fi
fi
```

Manual custom registry example:

```yaml
cache-registry: cache-registry.openchoreo-workflow-plane.svc.cluster.local:5100
cache-scope: main
cache-insecure: "true"
```

If a builder image lacks both `wget` and `curl`, skip the probe and either assume caching is disabled or use the builder's native cache failure behavior with `ignore-error` where supported. Verify this for the Paketo, GCP, and Ballerina builder images before implementation.

## Cache Key Strategy

Use cache refs scoped by namespace, project, component, workflow type, and branch.

Recommended refs:

```text
<cache-registry>/build-cache/buildkit/<namespace>/<project>/<component>:<branch>
<cache-registry>/build-cache/buildah/<namespace>/<project>/<component>:<branch>
<cache-registry>/build-cache/cnb/<namespace>/<project>/<component>:<branch>
<cache-registry>/build-cache/podman-buildpacks/<namespace>/<project>/<component>:<branch>
```

Use a sanitized cache scope:

- Prefer branch name when building a branch.
- Use `commit` or `detached` when only a commit is supplied.
- Replace unsupported tag characters with `-`.

Later improvement: import from both `main` and current branch, export only to current branch. Start with one cache ref per workflow to keep the first implementation simple.

## Dockerfile Builds: BuildKit

Update:

```text
samples/getting-started/workflow-templates/rootless-buildkit/containerfile-build.yaml
```

BuildKit should use registry cache import/export:

```sh
CACHE_ARGS=""
CACHE_REF="${CACHE_REGISTRY}/build-cache/buildkit/${IMAGE_NAME}:${CACHE_SCOPE}"

if [ "$CACHE_ENABLED" = "true" ]; then
  CACHE_ARGS="
    --import-cache type=registry,ref=${CACHE_REF}
    --export-cache type=registry,ref=${CACHE_REF},mode=max,image-manifest=true,oci-mediatypes=true,ignore-error=true
  "
else
  CACHE_ARGS=""
fi

buildctl-daemonless.sh build \
  --frontend dockerfile.v0 \
  --local context="$WORKDIR/$DOCKER_CONTEXT" \
  --local dockerfile="$DOCKERFILE_DIR" \
  --opt filename="$DOCKERFILE_NAME" \
  $BUILD_ARG_OPTS \
  $CACHE_ARGS \
  --output "type=docker,name=$IMAGE,dest=/mnt/vol/app-image.tar"
```

For insecure HTTP registry, generate BuildKit config:

```toml
[registry."cache-registry.openchoreo-workflow-plane.svc.cluster.local:5100"]
  http = true
  insecure = true
```

Set:

```sh
export BUILDKITD_FLAGS="--root=/storage --config=/tmp/buildkitd.toml"
```

## Dockerfile Builds: Buildah

Update:

```text
samples/getting-started/workflow-templates/rootless-buildah/containerfile-build.yaml
```

Buildah should use layer caching:

```sh
CACHE_ARGS=""
CACHE_REPO="${CACHE_REGISTRY}/build-cache/buildah/${IMAGE_NAME}"

if [ "$CACHE_ENABLED" = "true" ]; then
  CACHE_ARGS="
    --layers
    --cache-from ${CACHE_REPO}
    --cache-to ${CACHE_REPO}
    --cache-ttl 168h
  "
else
  CACHE_ARGS=""
fi

buildah build \
  --isolation chroot \
  $CACHE_ARGS \
  -t "$IMAGE" \
  -f "$WORKDIR/$DOCKERFILE_PATH" \
  $ENV_ARGS \
  $BUILD_ARG_FLAGS \
  "$WORKDIR/$DOCKER_CONTEXT"
```

Buildah pushes intermediate cache images to the registry directly; it is not the same manifest-based cache format BuildKit uses. Expect more cache tags and plan cleanup around the `build-cache/buildah/` prefix.

Configure insecure registry for Buildah/containers-common when `cache-insecure=true`:

```toml
[[registry]]
location = "cache-registry.openchoreo-workflow-plane.svc.cluster.local:5100"
insecure = true
```

Set:

```sh
export REGISTRIES_CONFIG_PATH=/tmp/registries.conf
```

## Buildpacks: CNB Lifecycle Cache Image

Update:

```text
samples/getting-started/workflow-templates/rootless-cnb/gcp-buildpacks-build.yaml
samples/getting-started/workflow-templates/rootless-cnb/paketo-buildpacks-build.yaml
samples/getting-started/workflow-templates/rootless-cnb/ballerina-buildpack-build.yaml
```

Remove the static no-cache behavior:

```sh
-skip-restore
```

When cache is enabled, replace local workflow-only cache with registry-backed CNB cache image. When the registry is unavailable, fall back to `-skip-restore` so behavior matches the current templates.

```sh
CACHE_IMAGE="${CACHE_REGISTRY}/build-cache/cnb/${IMAGE_NAME}:${CACHE_SCOPE}"

CACHE_ARGS="-skip-restore"
if [ "$CACHE_ENABLED" = "true" ]; then
  CACHE_ARGS="-cache-image=${CACHE_IMAGE}"
fi

/cnb/lifecycle/creator \
  -daemon \
  -app="$WORKDIR/$APP_PATH" \
  -run-image="$RUN_IMG" \
  $CACHE_ARGS \
  -platform=/mnt/vol/cnb-platform \
  "$SRC_IMAGE"
```

The CNB lifecycle will restore and update the cache image across workflows. This is the buildpack equivalent of cross-workflow layer caching.

Important details:

- `-cache-image` and `-daemon` are independent: the app image exports to the local Podman daemon, while the cache image is pulled/pushed directly to the registry.
- Remove the `cnb-cache` / `cnb-layers` emptyDir volume when registry cache is used; cache state lives in the registry.
- The Podman daemon used by CNB must be able to pull the run image and save the app image. The CNB lifecycle process must be able to push and pull the cache image.
- For an HTTP registry, configure the Podman sidecar or daemon pod with an insecure registry entry for `cache-registry...:5100`.

CNB registry auth resolution for `-cache-image`:

1. `CNB_REGISTRY_AUTH` env var.
2. Docker `config.json` from `$DOCKER_CONFIG` or `~/.docker/config.json`.
3. Anonymous access.

For the in-cluster cache registry, start with anonymous access. If auth is enabled later, mount a cache-specific secret and set:

```yaml
env:
  - name: DOCKER_HOST
    value: unix:///podman-run/podman.sock
  - name: DOCKER_CONFIG
    value: /etc/secrets/cache-registry-auth
  - name: CNB_PLATFORM_API
    value: "0.14"
```

`DOCKER_HOST` controls app image export to the daemon. `DOCKER_CONFIG` controls registry credentials for the cache image. They are independent.

Container layout for the current rootless CNB templates:

```yaml
sidecars:
  - name: podman-service
containerSet:
  containers:
    - name: main
      # CNB lifecycle creator only. OpenChoreo reads build logs from this container.
    - name: save-image
      dependencies:
        - main
      # podman save only. Writes /mnt/vol/app-image.tar for publish-image-rootless.
```

Rename the current `containerSet` container named `build` to `main`. Keep `save-image` separate so `podman save` output does not pollute the build logs.

## Buildpacks: Rootless Podman Build Step Uses `main`

Add or refactor the Podman-rootless buildpack template so the build step runs the actual build in a container named exactly `main`.

This is required because OpenChoreo currently reads logs only from the `main` container. Buildpack detect/restore/analyze/build/export logs must therefore come from `main`, not from a sidecar or helper container.

Target shape:

- Pod A, optional: rootless Podman daemon, created by a daemon template or separate workflow step if needed.
- Pod B, build step: buildpack `main` container, responsible for:
  - Buildpack build.
  - CNB/pack cache configuration.
  - Exporting/saving `/mnt/vol/app-image.tar` for the publish step.

Publishing remains a separate workflow step using `publish-image-rootless`.

If a daemon is needed outside the build pod, expose it through an internal service or workflow-local endpoint. Do not put the actual build execution in the daemon pod because those logs will not be read as build logs.

Cache behavior:

```sh
CACHE_IMAGE="${CACHE_REGISTRY}/build-cache/podman-buildpacks/${IMAGE_NAME}:${CACHE_SCOPE}"

pack build "$DEST_IMAGE" \
  --builder "$BUILDER" \
  --run-image "$RUN_IMG" \
  --docker-host "$DOCKER_HOST" \
  --path "$WORKDIR/$APP_PATH" \
  --cache-image "$CACHE_IMAGE"
```

If using direct lifecycle instead of `pack`, use the same CNB `-cache-image` approach described above.

Do not put registry credentials in buildpacks unless needed. Prefer a cache-only credential scoped to:

```text
build-cache/*
```

The final image push must continue to happen in the separate publish step with the existing registry push secret.

## Publish Step

The existing `publish-image-rootless` step can remain unchanged for Buildah, BuildKit, CNB, and Podman-rootless buildpack templates that output `/mnt/vol/app-image.tar`.

Buildpack build templates must not push the final image directly. They should produce the image artifact and let `publish-image-rootless` own registry authentication and final push behavior.

## CI Workflow Parameters

Add cache properties to rootless CI workflows:

```yaml
buildCache:
  type: object
  default: {}
  properties:
    enabled:
      type: boolean
      default: true
    scope:
      type: string
      default: ""
```

Pass these into build templates:

```yaml
- name: cache-registry
  value: ${parameters.buildCache.enabled ? "cache-registry.openchoreo-workflow-plane.svc.cluster.local:5100" : "none"}
- name: cache-scope
  value: ${has(parameters.buildCache.scope) && parameters.buildCache.scope != "" ? parameters.buildCache.scope : parameters.repository.revision.branch}
- name: cache-insecure
  value: "true"
```

For plain applied workflow templates, the default service DNS plus runtime probe means builds work either way: caching is used when the registry exists, and ignored when it does not. For Helm-rendered samples, set `cache-registry` to `"none"` when `.Values.cacheRegistry.enabled=false`.

## Helm and Template Disable Matrix

| Helm cache registry | Template `cache-registry` | Result |
|---|---|---|
| disabled | default service DNS | Probe fails; workflows build normally without caching |
| disabled | `"none"` | Workflows skip probe and build without caching |
| enabled | `"none"` | Cache registry exists but workflows do not use it |
| enabled | default/custom endpoint | Probe succeeds; workflows use layer caching |

This makes both sides explicit and avoids hidden coupling between Helm installation and separately applied templates.

## Validation

Validate on k3d and at least one managed-cluster-like environment.

Checks:

- Helm with `cacheRegistry.enabled=false` installs no cache registry resources.
- Rootless templates with cache defaults still build without a cache registry.
- Helm with `cacheRegistry.enabled=true` creates `cache-registry` and PVC.
- BuildKit first run exports cache; second run imports cache.
- BuildKit builds work when the cache registry is absent.
- Buildah first run exports cache; second run reuses layers.
- Buildah builds work when the cache registry is absent.
- Buildah HTTP cache works with insecure registry config.
- CNB first run creates cache image; second run restores buildpack layers.
- CNB builds work when the cache registry is absent by falling back to `-skip-restore`.
- CNB `main` container runs only lifecycle/build output.
- CNB `save-image` container runs after `main` and produces `/mnt/vol/app-image.tar`.
- Podman-rootless buildpack build logs appear in the build step's `main` container.
- Podman-rootless buildpack workflow still publishes through the separate `publish-image-rootless` step.
- Workflows use service DNS, not `host.k3d.internal`.
- Cache data persists across workflow-plane pod restarts when persistence is enabled.

Useful checks:

```sh
kubectl -n openchoreo-workflow-plane get deploy,svc,pvc cache-registry
kubectl -n openchoreo-workflow-plane port-forward svc/cache-registry 5100:5100
curl -s http://localhost:5100/v2/_catalog
```

## Open Decisions

- Whether cache is enabled by default in Helm. Recommended: enabled in dev values, disabled in base chart values until retention/auth are finalized.
- Whether the final image registry and cache registry should share credentials. Recommended: separate credentials.
- Whether to keep both Buildah and BuildKit long term. Recommended: implement cache for both during evaluation, then keep one as the default.
- Whether to implement registry garbage collection immediately. Recommended: document manual cleanup first, then add scheduled cleanup once cache paths stabilize.
